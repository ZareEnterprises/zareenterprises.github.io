NAVA technical overview01 / 17

One operator, three organizations, nine agents

Daniel runs AMBRA Live Productions, the music school EMN and the Berklee Perú club. NAVA is the single screen where all three meet. AI agents do the repetitive work. A person approves anything that matters.

  • A dashboard built on Tabler 1.6.1 and ApexCharts. It shows the day: brief, calendar, to do, alerts, finance, social reach and the lead pipeline.
  • A local hub, a small Python service, that serves data to the dashboard and keeps secret keys out of the browser.
  • A Supabase database in its own nava schema that stores everything the daily routine collects.
  • A team of agents, one per role, each with an identity file, skills and a memory file per company.
  • Automation in n8n for fixed steps such as invoices and the finance ledger.

NAVA technical overview04 / 17

Where decisions and leads live

Alerts & Decisions

Every agent that needs a human posts here. A card has the question, Accept and Deny buttons and a reply box. The title opens a large panel with all notifications, pending first and decided below.

  • Pending approvals are saved to disk, so a restart loses nothing.
  • The list only redraws when data changes, so a half-typed reply is never erased.
  • Every notification carries the name of the agent that raised it.

Clients tab

AMBRA and EMN side by side. Each company has an Outreach box with its latest lead search, then one card per lead.

  • Each card shows the lead, the reasons it fits and the full draft email.
  • Send sends the email and logs the lead in Airtable with status and next follow-up date.
  • A comment box plus Request changes sends the draft back to the Outreach agent.
  • Rejecting a lead stores it as Rejected, so it is never proposed again.
NAVA technical overview05 / 17

Nine agents, one per role

An agent is a role, not a program. Each role has an identity file, generic skills and a memory file for every company it serves. The same agent can work for AMBRA and EMN without ever mixing their data.

front door

Assistant

Receives every request, picks the company and role, routes it, and owns the cross-company view: digests, follow-ups, reminders and calendar.

sales

Outreach

Finds and ranks prospects, researches each one, writes short emails that cite real proof, and tracks every touch so nobody is contacted twice.

billing

Invoice

Turns a closed deal into a payment link and a PDF invoice for the right company, after a human confirms.

delivery

Coordinator

After payment, adds the client to Airtable and the company site, sends welcome emails and reminders, and closes the case.

money

Finances

Logs income, expenses and transfers in each company's Cash Ledger, reconciles Stripe and prepares the monthly close.

content

Socials

Cuts long event videos into clips, picks covers, writes captions and schedules posts through Metricool and Buffer.

brand

Visuals

The single source of truth for colors, fonts, logos and video rules. It works like a stylesheet for everything the companies publish.

build

Web

Builds and maintains the sites and web apps: Jekyll on GitHub Pages, Supabase backends, admin panels and invoice tools.

coaching

Trainer

Sales mentor and speaking coach. Prepares call structures, scripts, rescue phrases and role-play before live conversations with leads.

NAVA technical overview06 / 17

How an agent is assembled

Agents run as Claude Code sessions started inside a shared vault. A router file decides which files an agent may read for a given role and company.

  • Router. CLAUDE.md at the vault root maps role and company to the files to read. It also holds the language rules and the email rule.
  • Identity. Who the role is and how it works, generic and free of client names.
  • Skills. Plain-text procedures per role, and per role and company when they differ.
  • Memory. A file per role and company with what is done and what is pending.
  • Isolation. An agent never reads another company's folders unless Daniel authorises it for that task.
  • Changelog. Every saved rule or skill is logged with date, location and audience.

NAVA technical overview07 / 17

From a to-do card to a finished task

The task runner polls the hub every three seconds. Each queued task runs in its own thread with the tools of the agent that was picked. Runs time out after 30 minutes.

Drag

Daniel drags a To Do card onto an agent. The task is queued.

Investigate

claude -p starts with read-only tools and writes a plan.

Ask

If it needs an answer, it ends with a QUESTION line. The runner posts it to Alerts & Decisions.

Go ahead

Daniel replies, accepts or denies. Accepting the plan unlocks the act tools.

Act

The same Claude session resumes and writes files, drafts, rows or records.

Done

A DONE line with no open questions moves the card to Done. Otherwise it stays in Working On.

A finished task has a redo icon. It resumes the agent's session and runs only what was left pending, without repeating finished work.

NAVA technical overview08 / 17

Built so that a person stays in charge

Two tool tiers per agent

Each agent has a read-only list used while it investigates and an act list that is enabled only for the step after Daniel accepts its plan. Anything not on a list is denied.

No deletes

Coordinator can create and update Airtable records, never delete. The morning routine inserts rows and never replaces or removes them.

Email rule

Nothing is sent without explicit approval of the final version: text, recipients, sender account and signature. An earlier "send it" does not count.

Secrets stay on the server

The Supabase secret key lives in a local config read by the hub. The browser cannot receive it. Credentials are never written in notes.

Database lockdown

NAVA tables sit in their own schema with row level security on, no policies and no grants for the anon or authenticated roles. Only the secret key reads them.

Company isolation

Each task works with one company's folders, accounts and Stripe account. Money moving between AMBRA and EMN is a transfer, not income.

NAVA technical overview10 / 17

Fixed steps belong in n8n

The rule we followed: mechanical steps run in automation, and an AI model is used only where judgment is needed. That keeps cost low and behavior predictable.

Invoice

Check, approve, charge

A closed deal in Supabase triggers an AI judgment step that confirms the deal has enough data. The workflow then pauses and asks in NAVA before it creates a Stripe client, a payment link or an invoice.

Finances

Stripe to Cash Ledger

Every 30 minutes it reads new charges, writes them to the company's Google Sheet, reads the summary back to verify and updates the dashboard's finance data.

Coordinator

Payment trigger

Starts only when Outreach has confirmed the deal and the client has paid. Welcome emails and reminders go through approval.

Socials

Mixed

n8n schedules and publishes. The model is used only to write captions and pick covers.

NAVA technical overview11 / 17

The lead pipeline, end to end

  • Research. Web search, social profiles and email finders. Anything not confirmed, such as a date, name or address, is marked unconfirmed rather than guessed.
  • Classify. Prospect, partner, competitor or discard. Only prospects with a live event or need and a reachable contact get outreach.
  • Deduplicate. The agent reads the tracking sheet and the Airtable Leads table before proposing anyone.
  • Draft. Short, in the audience's language, with one specific detail, one line of proof with a link, the formats on offer and a single ask.
  • Review in Clients. Edit, comment, request changes, reject or send.
  • Track. Sending logs status, date and next follow-up in Airtable. The rule is a maximum of three follow-ups.

NAVA technical overview12 / 17

A chat that answers every message

The NAVA assistant lives inside the dashboard, with an orb for voice and an arrow that switches between voice only and the full chat.

  • The responder polls the hub and answers each new message with one claude -p call. There is no saved session and no tools.
  • Every call is given Daniel's saved memory, read fresh each time, plus today's calendar events and the To Do list.
  • Replies are plain text, posted back with POST /reply and read aloud.
  • After a restart, messages that never got an answer are answered first.
  • Real work, such as files, email or Supabase, is not done in the chat. It is routed to an agent.
NAVA technical overview13 / 17

The data layer and the hub API

Reads and writes to Supabase use the PostgREST profile headers for the nava schema. The dashboard never calls Supabase directly.

# reads GET /rows?day=YYYY-MM-DD today's items GET /messages chat history GET /approvals?all=1 Alerts & Decisions GET /tasks To Do, Working On, Done GET /agents agent list and tools GET /leads Clients tab GET /decisions # writes POST /message /reply POST /approval Accept, Deny, reply POST /task /task/rerun /task/dismiss POST /lead /lead/comment POST /leads/find start a lead search POST /followups/check POST /refresh/calendar
  • nava.nava_items holds brief items, calendar events, to do and pipeline counts, one row per item with a kind, title, url and a JSON detail.
  • nava.deals holds closed deals. A new row is the trigger for the Invoice workflow.
  • Local JSON files in the dashboard's data folder hold tasks, approvals, leads, finance and the updates log.
  • Updates log. Every improvement to NAVA is added with a small script and shows in the Updates panel with its date.
